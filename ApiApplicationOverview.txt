FINTECH APPLICATION - CORE APPLICATION FLOW & API INTEGRATION GUIDE
===================================================================

PURPOSE
-------

This document describes the complete application flow, API dependency order, authentication requirements, account architecture, and financial transaction flow of the fintech application.

It is intended to serve two purposes:

1. Core functional documentation for understanding how the fintech application works.
2. Integration guide for developers who want to build their own frontend, portal, or application on top of the provided API stack.

The API stack follows a sequential authorization and configuration flow. Certain APIs must be called before the user can access protected application services.


1. INITIAL APPLICATION CONFIGURATION
------------------------------------

Before a client application can use the API stack, the required domain and API-key configuration must exist in the database.

STEP 1 - INSERT DOMAIN AND X-API-KEY MAPPING

Create a mapping document between the application domain and its corresponding `x-api-key`.

The mapping establishes which API key is authorized to communicate with the API stack for a particular application/domain.

Conceptually:

    Domain
       |
       +---- x-api-key
       |
       +---- Application Configuration

Example:

    example-client.com
          |
          +---- client-x-api-key


STEP 2 - INSERT DNS CONFIGURATION

Insert the DNS configuration document into the database.

The DNS configuration contains the information required by the application to determine which configuration should be used for the requesting domain.

The DNS configuration must be associated with the appropriate domain/application.

The domain and x-api-key mapping and the DNS configuration therefore establish the initial application configuration required before normal API access begins.


2. DNS CONFIGURATION INITIALIZATION
-----------------------------------

STEP 3 - CALL GET DNS CONFIG API

The client application must call the Get DNS Configuration API to load the DNS configuration associated with the domain specified in the current session.

The API determines the appropriate DNS/application configuration based on the domain information available in the session.

This step is mandatory before calling the application's service APIs.

IMPORTANT SESSION BEHAVIOR

The application session is valid for approximately 12 minutes.

The session is destroyed after 12 minutes.

Therefore:

    Get DNS Configuration API
            |
            +---- Session configuration loaded
            |
            +---- Session remains valid for approximately 12 minutes

The client application must call the Get DNS Configuration API:

    - Every 12 minutes, OR
    - Before calling another service API if more than 12 minutes have elapsed since the previous DNS configuration call.

Recommended client-side flow:

    Application Start
          |
          ↓
    Get DNS Configuration
          |
          ↓
    Session Configuration Loaded
          |
          ↓
    Call Application APIs
          |
          ↓
    12 Minutes Elapsed?
       /          \
     NO            YES
      |             |
      |             ↓
      |      Get DNS Configuration
      |             |
      +-------------+
                    |
                    ↓
              Continue APIs


3. USER REGISTRATION
--------------------

STEP 4 - SIGN UP

After the application configuration has been initialized, the user can register with the application.

The signup process creates the user's basic application profile.

Typical flow:

    Client Application
          |
          ↓
       Sign Up
          |
          ↓
      User Created
          |
          ↓
       User Sign In


4. AUTHENTICATION AND AUTHORIZATION
-----------------------------------

STEP 5 - LOGIN

Before protected service APIs can be accessed, the user must authenticate.

The login API validates the user's credentials and establishes the authentication/session context required for subsequent authorization operations.

The general authentication flow is:

    Sign Up
       |
       ↓
     Login
       |
       ↓
    Send 2FA
       |
       ↓
   Verify 2FA
       |
       ↓
 Authorized User
       |
       ↓
 Protected Service APIs


STEP 6 - SEND 2FA

After successful login, the application must initiate the 2FA process.

The Send 2FA API sends the second-factor authentication mechanism required by the application.

The user cannot proceed to protected service operations until the required 2FA verification process is completed.


STEP 7 - VERIFY 2FA

The user submits the received 2FA verification information.

The Verify 2FA API validates the submitted 2FA information.

After successful verification, the user becomes authorized to access the protected service APIs.

IMPORTANT:

Before calling any protected service API, the following authorization sequence must be completed:

    Login
      ↓
    Send 2FA
      ↓
    Verify 2FA
      ↓
    Authorized Service Access

A client application should not directly call protected service APIs before completing this sequence.


5. USER ONBOARDING
------------------

STEP 8 - SUBMIT USER ONBOARDING DETAILS

After authentication and authorization, the user can complete onboarding.

The onboarding process contains:

    - User address details
    - Billing address
    - Delivery address
    - Bank account details

The onboarding API creates or updates the user's address and bank information.

Address information can be updated when required.

Bank information follows the verification lifecycle.

If the bank account is:

    NEW
       ↓
    Create bank details
       ↓
    Unverified

If the bank account exists and is:

    UNVERIFIED
       ↓
    Update bank details

If the bank account is:

    VERIFIED
       ↓
    Bank details cannot be updated through the normal onboarding API.


6. BANK VERIFICATION
--------------------

STEP 9 - SEND BANK VERIFICATION REQUEST

After onboarding, the application generates a bank verification request.

A unique verification request ID is associated with the user's bank details.

The administrator receives a bank verification email.

The email contains the verification action required to approve or reject the user's bank account.

Flow:

    User Onboarding
          |
          ↓
    Bank Details Created
          |
          ↓
    Verification Request Generated
          |
          ↓
    Admin Verification Email
          |
          ↓
    Admin Approves / Rejects


STEP 10 - ADMIN APPROVES BANK ACCOUNT

If the administrator approves the bank account:

    1. Bank details are marked as verified.
    2. A cardholder_id is generated.
    3. The cardholder_id is stored against the user's bank details.
    4. The same cardholder_id is stored against the user.
    5. The application creates the user's fiat funding account.
    6. The application creates the user's crypto deposit account.

The bank verification transaction should ensure that these related operations are completed consistently.

Conceptually:

    BANK APPROVED
          |
          +---- is_verified = true
          |
          +---- Generate cardholder_id
          |
          +---- Store cardholder_id against User
          |
          +---- Store cardholder_id against Bank Details
          |
          +---- Create Fiat Funding Account
          |
          +---- Create Crypto Deposit Account


STEP 11 - ADMIN REJECTS BANK ACCOUNT

If the administrator rejects the bank account:

    - Bank details remain unverified.
    - No new cardholder_id is created as part of the rejection.
    - Funding accounts are not created as part of the rejection.
    - The user can update the bank details and go through verification again.


7. APPLICATION-PROVIDED FIAT FUNDING ACCOUNT
--------------------------------------------

STEP 12 - FIAT FUNDING ACCOUNT

After successful bank verification, the application provides the user with a USD fiat funding account.

This is different from the user's original external bank account.

The user's original bank account is used during onboarding and verification.

The application-provided fiat funding account acts as the entry point for fiat money into the application.

Conceptually:

    User External Bank
          |
          | Fiat Transfer
          ↓
    Application Fiat Funding Account
          |
          ↓
    User Wallet
          |
          ↓
    Cards / FX / Payouts


The fiat funding account contains information such as:

    - User ID
    - Cardholder ID
    - Account holder name
    - Account number
    - Currency
    - Account balance
    - SWIFT code
    - IBAN
    - Bank name
    - Active status

The initial balance is:

    0 USD


8. APPLICATION-PROVIDED CRYPTO DEPOSIT ACCOUNT
-----------------------------------------------

STEP 13 - CRYPTO DEPOSIT ACCOUNT

After successful bank verification, the application also provides the user with a crypto deposit account.

The crypto deposit account contains:

    - User ID
    - Cardholder ID
    - Network
    - Asset
    - Deposit address
    - Account balance
    - Active status

The deposit address represents the address to which the user can send cryptocurrency.

Real-world concept:

    User External Crypto Wallet
              |
              | Blockchain Transaction
              ↓
       Application Deposit Address
              |
              ↓
       Crypto Deposit Account
              |
              ↓
          Crypto Wallet


For the demo application, the crypto funding API simulates the incoming blockchain transaction rather than performing an actual blockchain transfer.


9. FIAT FUNDING
---------------

STEP 14 - PREFUND FIAT FUNDING ACCOUNT

The user can fund the application-provided fiat funding account.

In a real fintech environment:

    User External Bank
          |
          | Bank Transfer
          ↓
    Application Funding Account

In the demo environment:

    Prefund Fiat Funding Account API
                  |
                  ↓
        Increase Funding Balance


Example:

    Current Balance = $500
    Prefund Amount  = $100
    New Balance     = $600


IMPORTANT:

The prefunding operation does not directly increase the user's wallet.

It only represents money entering the application funding account.

The funding account and wallet are separate financial layers.


10. CRYPTO FUNDING
------------------

STEP 15 - PREFUND CRYPTO FUNDING ACCOUNT

The user can also simulate an incoming crypto transaction.

In a real-world environment:

    External Crypto Wallet
             |
             | Blockchain Transfer
             ↓
       Deposit Address
             |
             ↓
     Crypto Deposit Account
             |
             ↓
       Crypto Wallet


In the demo environment:

    Prefund Crypto Funding Account API
                  |
                  ↓
       Increase Crypto Funding Balance


Example:

    Existing USDC Balance = 500 USDC
    Incoming Amount       = 250 USDC
    New Balance            = 750 USDC


The network and asset identify the specific crypto deposit account.

Example:

    Network = POLYGON
    Asset   = USDC

means that the POLYGON/USDC deposit account is used.


11. WALLET CREATION
-------------------

STEP 16 - CREATE USER WALLET

After funding accounts are available, the user can create application wallets.

Supported wallet currencies include:

    - USD
    - EUR
    - SGD
    - USDC
    - USDT

A wallet represents money that can be used for application-level financial operations.

The wallet is different from the funding account.

Funding Account:

    Represents incoming funds.

Wallet:

    Represents funds available for application transactions.


12. LOAD FIAT WALLET
--------------------

STEP 17 - LOAD FIAT WALLET

The user can transfer funds from the fiat funding account into a fiat wallet.

Flow:

    Fiat Funding Account
            |
            ↓
        USD Wallet


Example:

    Fiat Funding Account = $1,000
    USD Wallet           = $0

    Load Wallet = $500

    Result:

    Fiat Funding Account = $500
    USD Wallet           = $500


The application should verify:

    1. Funding account exists.
    2. Funding account is active.
    3. Wallet exists.
    4. Wallet is active.
    5. Funding account has sufficient balance.
    6. Requested amount is valid.
    7. Currency is supported.


13. LOAD CRYPTO WALLET
----------------------

STEP 18 - LOAD CRYPTO WALLET

Crypto funds follow the same basic architecture.

Flow:

    Crypto Deposit Account
            |
            ↓
        Crypto Wallet


Example:

    USDC Funding Account = 1,000 USDC
    USDC Wallet          = 0 USDC

    Load Wallet = 600 USDC

    Result:

    USDC Funding Account = 400 USDC
    USDC Wallet          = 600 USDC


The network identifies the blockchain environment of the deposit account.

The asset identifies the cryptocurrency.

The wallet represents the user's usable application balance.


14. WALLET AS THE PRIMARY TRANSACTION BALANCE
----------------------------------------------

STEP 19 - APPLICATION TRANSACTION SOURCE

Once funds have been loaded into the wallet, the wallet becomes the primary source for application financial operations.

The application should generally follow:

    Funding Account
          ↓
        Wallet
          ↓
    Application Transaction


Examples:

    Wallet
      |
      +---- Card Funding
      |
      +---- Card Spending
      |
      +---- FX Conversion
      |
      +---- Payout
      |
      +---- Other Supported Operations


The original funding account should not normally be used directly for card spending or beneficiary payouts.

This separation makes the application architecture closer to a real fintech wallet system.


15. FX / CURRENCY CONVERSION
----------------------------

STEP 20 - GENERATE FX QUOTE

The application provides currency conversion functionality.

Example:

    USD → EUR

The FX service determines:

    - Source currency
    - Destination currency
    - Source amount
    - FX rate
    - Destination amount
    - Applicable fee
    - Total amount to be deducted


STEP 21 - EXECUTE FX CONVERSION

After the user accepts the quote:

    1. Source wallet is identified.
    2. Source wallet balance is checked.
    3. Required source amount is deducted.
    4. Applicable fee is deducted.
    5. Destination amount is calculated.
    6. Destination wallet is credited.


Example:

    USD Wallet
        |
        | FX Conversion
        ↓
    EUR Wallet


16. CARD CREATION
-----------------

STEP 22 - CREATE CARD

After the user has completed the required verification and has a valid cardholder_id, the user can request a card.

The application:

    1. Validates the user.
    2. Validates the cardholder ID.
    3. Creates the card.
    4. Applies configured card limits.
    5. Associates the card with the user.


17. CARD FUNDING
----------------

STEP 23 - FUND CARD

The user can fund the card using an eligible wallet.

Flow:

    User Wallet
         |
         ↓
       Card


Before funding:

    - Wallet must exist.
    - Wallet must be active.
    - Card must exist.
    - Card must be active.
    - Sufficient balance must exist.
    - Funding amount must be valid.
    - Applicable limits must be respected.


18. CARD TRANSACTION
--------------------

STEP 24 - CARD SPENDING

When the user spends using the card:

    Card
      |
      ↓
    Card Transaction
      |
      ↓
    Hold / Pending
      |
      ↓
    Completed


The transaction may initially be represented as:

    transaction_type = HOLD
    transaction_status = PENDING


After successful completion, the transaction is finalized.

Card transactions ultimately consume funds that originated from the user's wallet.


19. BENEFICIARY MANAGEMENT
--------------------------

STEP 25 - CREATE BENEFICIARY

The user can create a beneficiary for payout operations.

Beneficiary information can include:

    - Beneficiary name
    - Bank account number
    - Bank name
    - SWIFT/BIC
    - IBAN
    - Payout currency
    - Other required banking information


The beneficiary is associated with the user and can subsequently be used for payout transactions.


20. PAYOUT QUOTE
----------------

STEP 26 - GENERATE PAYOUT QUOTE

Before executing a payout, the user generates a payout quote.

The quote can contain:

    - Source currency
    - Source amount
    - Destination currency
    - Destination amount
    - FX rate
    - Fee
    - Total amount required


The quote only represents the proposed payout terms.

The quote does not execute the payout.

Example:

    USD Wallet
         |
         ↓
    Payout Quote
         |
         ↓
    Destination Currency
         |
         ↓
    Beneficiary


21. EXECUTE PAYOUT
------------------

STEP 27 - EXECUTE PAYOUT QUOTE

When the user accepts the quote:

    1. Quote is validated.
    2. Quote validity is checked.
    3. Source wallet is identified.
    4. Wallet balance is checked.
    5. Required amount is deducted.
    6. Applicable fee is deducted.
    7. Funds are moved into the payout holding flow where applicable.
    8. Payout transaction is created.
    9. Payout starts with PENDING status.


Flow:

    User Wallet
         |
         ↓
    Payout Holding
         |
         ↓
    Beneficiary / External Bank


22. PAYOUT PROCESSING
---------------------

STEP 28 - PROCESS PENDING PAYOUT

The demo application uses a scheduled process to simulate an external payout provider.

The transaction lifecycle is:

    PENDING
       ↓
    PROCESSING
       ↓
    SUCCESS


The scheduled process periodically checks pending transactions.

The demo process simulates the external banking/payment provider and eventually marks the payout as successful.


23. FEES

STEP 29 - APPLY FINANCIAL FEES

The fee configuration should determine:

26. ACCOUNT RESPONSIBILITIES
----------------------------

USER EXTERNAL BANK ACCOUNT

Purpose:

    - Submitted by the user during onboarding.
    - Used for bank verification.
    - Represents the user's external banking relationship.

This account is not the application's wallet.


FIAT FUNDING ACCOUNT

Purpose:

    - Application-provided USD funding account.
    - Represents incoming fiat funds.
    - Acts as a funding pool.
    - Used as a source for wallet loading.

It is not the primary account used for cards and payouts.


CRYPTO DEPOSIT ACCOUNT

Purpose:

    - Application-provided crypto deposit account.
    - Contains a deposit address.
    - Represents incoming crypto funds.
    - Used as a source for crypto wallet loading.


WALLET

Purpose:

    - Represents funds available for application operations.
    - Used for card funding.
    - Used for payouts.
    - Used for currency conversion.
    - Represents the user's spendable application balance.


CARD

Purpose:

    - Payment instrument.
    - Funded from an eligible wallet.
    - Used to perform card transactions.


PAYOUT HOLDING

Purpose:

    - Temporary state/account used during payout processing.
    - Represents funds that have been committed to an outgoing payout but have not yet reached the beneficiary.

   10. User submits onboarding details.

   15. If approved, bank details are marked verified.

29. IMPORTANT API INTEGRATION RULES
-----------------------------------

RULE 1 - DNS CONFIGURATION

The client must load DNS configuration before using the application service APIs.

RULE 2 - 12-MINUTE SESSION

The session is destroyed after approximately 12 minutes.

Therefore the Get DNS Configuration API must be called:

    - Every 12 minutes, or
    - Before another API call if more than 12 minutes have elapsed since the previous DNS configuration call.

RULE 3 - AUTHORIZATION

Protected service APIs must not be called directly after signup.

The required authentication flow is:

    Login
       ↓
    Send 2FA
       ↓
    Verify 2FA
       ↓
    Protected APIs


RULE 4 - BANK VERIFICATION

The user cannot access the complete financial functionality until the required bank verification process is successfully completed.


RULE 5 - FUNDING ACCOUNTS VS WALLETS

Funding accounts and wallets must be treated as separate financial entities.

Funding Account:

    Incoming money.

Wallet:

    Application spending/transaction balance.


RULE 6 - WALLET AS TRANSACTION SOURCE

Cards and payouts should use eligible wallet balances rather than directly using the original funding account balance.


RULE 7 - QUOTE VS EXECUTION

A quote only defines transaction terms.

Creating a quote must not execute the financial transaction.

Execution happens only after the user explicitly executes/accepts the quote.


RULE 8 - DEMO EXTERNAL PROVIDERS

Where the demo application does not integrate with an actual external bank, card processor, blockchain provider, or payout provider, the corresponding API or scheduled process should explicitly simulate the external operation.

31. CORE FINANCIAL ARCHITECTURE PRINCIPLE
-----------------------------------------

The application follows the following fundamental financial architecture:

    EXTERNAL SOURCE
          ↓
    FUNDING ACCOUNT
          ↓
        WALLET
          ↓
    FINANCIAL OPERATION


For fiat:

    External Bank
          ↓
    Fiat Funding Account
          ↓
    Fiat Wallet
          ↓
    Card / FX / Payout


For crypto:

    External Crypto Wallet
          ↓
    Crypto Deposit Account
          ↓
    Crypto Wallet
          ↓
    Supported Crypto Operation


This separation is the core principle of the application's financial architecture.

The funding account represents money entering the application.

The wallet represents money available for application-level use.

Cards represent payment instruments.

Payouts represent outgoing payments.

Holding accounts represent funds committed to an operation that is still being processed.

Transactions provide the financial record of activity.

The complete architecture is therefore:

    CONFIGURATION
         ↓
    AUTHENTICATION
         ↓
    ONBOARDING
         ↓
    VERIFICATION
         ↓
    FUNDING ACCOUNTS
         ↓
    WALLETS
         ↓
    FINANCIAL OPERATIONS
         ↓
    TRANSACTIONS
         ↓
    SETTLEMENT / COMPLETION
